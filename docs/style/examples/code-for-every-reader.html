Code for every reader

Readers arrive with different habits. A Python analyst expects plain functions, dicts and for-loops. Someone from functional programming expects pure functions: data in, data out. Someone who learned basic OOP expects classes. Code is easiest for all three when it stays where those habits overlap.

ReaderFeels at home withGets lost in
Python / data analystFunctions, dicts, lists, for loops, list comprehensionsChained one-liners, this, JS truthiness tricks
Functional stylePure functions, map/filter, no hidden stateObjects that change underneath them, deep class trees
Basic OOPClasses with a clear job, named methodsPoint-free pipelines, reduce everywhere, currying
Shared groundPlain functions · plain data · loops and early returns · names from the problem's own vocabulary · inputs you can see in the signature

One question sits under every practice below: how much does the reader have to hold in their head? Each case reduces one or more of four things.

01 · your question

The one-line wrapper

jumpshidden state

Your instinct is right. A function whose whole body is one library call adds a name the reader must learn and hides nothing in exchange. Everyone knows requests.get. Nobody knows get_text until they open another file to find out it is requests.get.

The wrapper also creates a false promise. A reader seeing a custom function assumes it handles something: timeouts, errors, encoding. This one handles nothing, so the guess is wrong in a way that only shows up in production.

Why people write them anyway

  • "We might switch HTTP libraries." This rarely happens, and when it does a search-and-replace is cheap. The principle that pushes back is YAGNI: you aren't gonna need it.
  • "It's easier to mock in tests." Sometimes true, but Python's unittest.mock.patch("requests.get") patches the library call directly. Make the seam when you write the test that needs it, not before.
  • Habit from enterprise Java, where every dependency sits behind an interface "for flexibility".
  • Line-count rules ("no function over 20 lines") that push people to split things that belonged together.
  • AI models do it too. They learned from codebases full of such wrappers, and splitting code into many small named pieces looks organised. Left unguided, an AI tends to add layers.
02 · the other side

When a wrapper earns its place

jumps

The test is whether the function hides more than it costs. John Ousterhout calls this deep versus shallow (A Philosophy of Software Design): a deep function has a small interface and a lot of decisions behind it. A shallow one has an interface as large as its body.

Rule

Wrap a library call only when the wrapper adds a decision (a default, a retry, an error message, a domain name) and it has two or more callers. Otherwise call the library directly.

03

Splitting a recipe into crumbs

jumps

The same problem at the scale of one file. A short, linear task gets cut into helpers that are each used once. Every helper is easy on its own; the task as a whole is now spread over seven places.

Extract a piece into its own function when one of these is true:

  • It is used in two or more places. (Many teams wait for the third: the rule of three.)
  • It is pure logic worth its own test, like this repo's coverageCells.
  • Its name tells the reader something the body can't say quickly, such as a tricky regular expression or a formula.

"It made the function shorter" is not on the list. Length is a weak signal; how many things the reader must track is the real one.

04

Class trees for one case

jumpshidden state

A base class, a subclass and a factory, built for export formats that might come one day. Today there is one.

To follow A, the reader traces export() → prepare() in the parent → serialize() in the child, chosen by the factory. B is one function a Python, FP or OOP reader all read the same way. When a second format really arrives, an if (format === "csv") inside the function is usually enough; a class tree is worth it at perhaps the fourth.

Rule

Start with a function. Use a class for something with a lifecycle that owns state and behaviour together (open → render → close). Add inheritance only when two real variants exist, not imagined ones.

05

Plain data over accessor classes

hidden stateidioms

A Python reader sees a dict (or a dataclass). An FP reader sees a value. The JSDoc type gives you the safety a class would, checked by tsc, which this repo already runs. Plain objects also print readably in the console and go straight into storage, which is how store.js can import and export a book.

Keep a class (or a validating makeSection() function) when something must stay true on every change, such as fromPage ≤ toPage.

06 · from this repo

Compute first, touch the world last

hidden statejumps

Keep the thinking in one function that takes data and returns data. Put the DOM, storage and network in a second, thin function. Gary Bernhardt's name for this is functional core, imperative shell. The coverage strip in viewer/coverage.js already does it.

test/ui-logic.test.js checks coverageCells with plain objects and no browser. Each reader recognises the shape: FP sees a pure function, Python sees a function returning a list, OOP loses nothing. This is the practice that pays most for the least effort.

07

Loops versus chains

idioms

Neither style always wins, so here are both directions.

Case 1: the loop is clearer

Modern browsers also have Object.groupBy(notes, (n) => n.type). A well-named built-in beats both, as long as your readers have met it.

Case 2: the chain is clearer

Rule

map/filter for one-step transforms, one step per line. A for…of loop when building up a structure or doing several things per item. reduce only for sums. No nested ternaries.

08

Guard clauses over nesting

nesting

In B, each line closes a case and the reader can forget it. The real work sits at the bottom, not indented four levels deep. Python readers know this as "return early"; it is the same in every language.

09

A short list of allowed idioms

idioms

Every language has shorthand that insiders read instantly and visitors misread. You don't need to ban all of it. Pick a few that earn their keep, write them down, and keep the rest out.

IdiomMeansTrap for visitorsVerdict
a ?? bb if a is null/undefinedEasy to confuse with ||Allow, very useful
a?.ba.b, or undefined if a is missingLong chains hide which part can be missingAllow, one or two links
a || 2020 if a is "falsy"0 and "" are falsy: a typed 0 becomes 20Prefer ??
!!xx as true/falseLooks like a typo to a Python readerWrite the comparison
+strConvert to numberInvisible; "" becomes 0Use Number(str)
ok && doThing()Run if okAn expression used as a statementUse if
[...new Set(a)]Remove duplicatesThree concepts in nine charactersFine with a comment

This repo uses book?.chunks ?? {} in coverage.js, and it reads fine once you know the two operators. That is the point of a list: two operators are learned once, a dozen are a barrier.

10

Names from the problem

hidden statejumps
  • Use the domain's words: page, section, note, recap. A reader who knows the product can then guess what code does.
  • One word per concept. Worth checking here: the store keys sections as chunks while the UI and docs say "section". A newcomer has to discover that they are the same thing. Either pick one word or say so where the type is defined.
  • Units in the name: timeoutMs, maxTokens, timeout_s.
  • Booleans as yes/no questions: isStale, hasNotes.
  • Functions named for what they return (coverageCells) or what they do (renderCoverage), never process, handle or doStuff.

Comments that say why

hidden state

The code already says what. B records a decision that looks wrong at first glance and protects it: without the comment, a well-meaning "cleanup" to addEventListener brings back the bug. The traps list in this repo's CLAUDE.md (pdf.js URLs must be absolute; render() hangs in a hidden tab) is the same practice at project scale.

12

Every input in the signature

hidden state

In A, the result of renderRail() depends on whoever last wrote currentBook, and the reader can't tell from here. In B the signature lists every dependency. For three or more parameters, or any true/false flag, pass one options object so each value carries its name at the call site.

13

Errors caught where they mean something

hidden statenesting

Swallowing an error turns a clear message at the source into a confusing one far away. Catch only where you can do something: show the reader a message, retry, or fall back on purpose.

14

async/await over callback pyramids

nestingidioms

Python readers know async/await from asyncio; it is one of the few constructs that looks almost the same in both languages, so lean on it.

15

Keep things next to their only user

jumps

Folders called utils/, helpers/ or constants/ group things by what they are, not by what they're for, so reading one feature means opening four files. A value lives beside its only user and moves to a shared module when it gets a second one. This repo's flat viewer/ folder, one file per feature, is already close to this.

16

Don't change what you were handed

hidden state

Python readers know this trap from functions that append to a list you passed in, or pandas' inplace=True. Don't overdo the cure: changing an array you just created inside the same function, as in practice 03, is fine. The rule is about other people's data.

Putting it to work

How to get an AI to write this way

An AI follows three things, roughly in this order of strength: the code around it, the written rules it is given, and what you ask it to check. Use all three.

1. The code nearby is the loudest instruction

Models imitate the files they read. Claude Code's own instructions tell it to write code that reads like the surrounding code. Clean files breed clean copies, and one tangled file breeds tangled copies. So name an exemplar: "write new modules like viewer/coverage.js: a pure function that computes, a thin one that draws." A pointer to a real file carries more than a paragraph of adjectives.

2. Write rules a reviewer could check

"Write clean, readable code" can't be checked, so the model fills it with its own idea of clean, and that idea leans toward more layers. A rule like "no function with one caller unless it is pure and tested" can be checked line by line. Give each rule its reason too, so the model can handle cases the rule didn't foresee. A section like this could go in CLAUDE.md:

CLAUDE.md · a draft section
## Code style: written for readers from any background

Readers may know Python, functional style or basic OOP, and not modern JS
idioms. Aim for the fewest concepts per screen. Model file: viewer/coverage.js.

- Call libraries directly. Wrap one only when the wrapper adds a decision
  (a default, a retry, an error message) AND has two or more callers.
- Don't split a function into helpers used once. Extract on the second use,
  or when the piece is pure logic that gets its own test.
- Functions and plain objects first. A class only for something with a
  lifecycle (open/close, start/stop). No inheritance without two real variants.
- Pure computation in one function; DOM, storage and network in another.
- for...of when building up a result; map/filter for one-step transforms,
  one step per line; reduce only for sums; no nested ternaries.
- Allowed idioms: ?. ?? spread. Not: !!x, +str, a || default, cond && action().
- Return early instead of nesting; at most three levels deep.
- Every input in the signature; no module-level mutable state. Three or more
  parameters, or any boolean flag: pass an options object.
- Let errors throw; catch only where the reader can be told something.
- Names from the book's vocabulary, one word per concept; units in names
  (timeoutMs); booleans as questions (isStale).
- Comments say why, never what.

3. Ask for the review in a reader's terms

After a change, ask the AI to read its own diff as one of your readers. Any idiom it has to explain is a candidate to simplify. Prompts that work:

Read your diff as a Python analyst who has never written JavaScript. List every line where they would need to look something up.
For each new function, list its callers. Inline any with a single caller unless it's pure and tested.
What would this change look like with no new files and no new classes? Show me that version first.

4. Ask for the plain version first

Abstraction added early is shaped by guesses. Abstraction added when a second real use shows up is shaped by that use. Say so up front: "Write the most direct version. I'll ask for structure when I need it." This matches the line already in this repo's CLAUDE.md: prefer the simplest thing that genuinely works.

5. Mechanical checks, if you want them

ESLint has rules for some of this (complexity, max-depth, no-nested-ternary, no-param-reassign). The cost is a dev dependency and a config file to look after, and this repo has so far chosen tsc only. The written rules plus a reader-terms review cover most of the same ground without installing anything.

6. Don't overcorrect

"Fewer functions" is not the goal. A 300-line function that does five unrelated things is as hard to follow as forty tiny ones. The goal is that each function does one thing you could name out loud, and every name a reader meets is worth learning.

The one-line test

Could someone who knows only the basics of the language understand this file by reading it top to bottom, without opening another?
